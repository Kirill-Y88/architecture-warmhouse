### 2. Анализ архитектуры монолитного приложения

- СУБД: PostgreSQL 16
- Схема БД: одна таблица sensors
- Взаимодействие: "Клиент" - "приложение" - "сервис измерения температуры" через REST API
- Развертывание: docker - docker-compose

### 3. Определение доменов и границы контекстов

 - Домен: "Учет датчиков и мониторинг температуры"
   - поддомены:
     - Реестр датчиков
     - Температурная телеметрия
 - Контексты:
   - Реестр датчиков. 
     - Ответственность: управление записями об устройствах — создать, прочитать, обновить, удалить датчик и его атрибуты.
   - Температурная телеметрия
     - Ответственность: получение текущих показаний температуры.
 - В данном случае, на этапе монолита, поддомены и контексты совпадают
   

**Предметная область (по кодовой базе):** система «умного дома» (Warmhouse) для мониторинга температуры в помещениях. Текущий монолит (`apps/smart_home`) — Go-приложение (Gin + PostgreSQL), которое ведёт реестр датчиков и получает текущие показания температуры из внешнего `temperature-api`. Управления отоплением, алертов и пользователей в коде нет.

#### 3.1. Что реально есть в коде

- Модели (`models/sensor.go`): `Sensor`, `SensorCreate`, `SensorUpdate`, `SensorType` (единственное значение — `temperature`).
- БД (`init.sql`): одна таблица `sensors` (`id, name, type, location, value, unit, status, last_updated, created_at`) + индексы.
- Доступ к данным (`db/db.go`): `DB` (пул `pgxpool`) с методами CRUD.
- HTTP-слой (`handlers/sensors.go`): CRUD датчиков, `PATCH /:id/value`, `GET /temperature/:location`, обогащение ответов живой температурой.
- Интеграция (`services/temperature_service.go`): `TemperatureService` (HTTP-клиент) и `TemperatureResponse`.
- Внешний сервис (`docker-compose.yml`): `temperature-api` на порту `8081`.

#### 3.2. Ограниченные контексты (Bounded Contexts)

На основе кода выделяется **два** контекста.

**Контекст 1. Реестр датчиков (Sensor Registry)**
- Ответственность: управление записями об устройствах — создать, прочитать, обновить, удалить датчик и его атрибуты (`name`, `type`, `location`, `unit`), а также хранение «кэша последнего значения» (`value`, `status`, `last_updated`).
- В коде: `models` + таблица `sensors` + CRUD в `db`/`handlers`.
- Язык: `Sensor` = запись/паспорт устройства; `value` = последнее известное значение (пишется через `PATCH /:id/value`); `status` = сохранённое состояние (`active`/`inactive`).

**Контекст 2. Температурная телеметрия (Temperature Telemetry)**
- Ответственность: получение текущих показаний температуры из внешнего API.
- В коде: `services/temperature_service.go` + `temperature-api` + `GetTemperatureByLocation` + обогащение в `GetSensors`/`GetSensorByID`.
- Язык: `value` = живое показание; `timestamp` = момент измерения; `status` = состояние источника данных; `sensor_id`/`location` = ключи запроса.

#### 3.3. Граница контекстов (один термин — два смысла)

| Термин | Реестр датчиков | Телеметрия |
|---|---|---|
| `Sensor` | запись/паспорт устройства (таблица `sensors`) | источник данных, по `sensor_id` которого берётся показание |
| `value` | последнее известное значение в БД (пишется через `PATCH`) | живое показание из API (не сохраняется) |
| `status` | сохранённое состояние устройства | состояние источника данных из API |
| `location` | атрибут устройства (комната) | ключ запроса/атрибут показания |
| `id` / `sensor_id` | первичный ключ `sensors.id` | `sensor_id` в ответе/пути API |

#### 3.4. Карта контекстов (Context Map)

- **Sensor Registry → Temperature Telemetry:** *Customer/Supplier*. Реестр (обработчики) — потребитель: вызывает телеметрию по `sensor.ID` (`GetTemperatureByID`) и по `location` (`GetTemperature`).
- Точка интеграции — `handlers/sensors.go`: реестр и телеметрия сшиты в одном обработчике (признак монолита — контексты ещё не разделены по модулям).

#### 3.5. Типы поддоменов

По коду выделить «доменное ядро» нельзя — бизнес-логики, дающей конкурентное преимущество, нет:
- Реестр датчиков — поддерживающий поддомен.
- Температурная телеметрия — поддерживающий поддомен.

#### 3.6. Что НЕ выделяем (в коде отсутствует)

- Управление отоплением — нет таблиц/моделей/эндпоинтов.
- Уведомления/алерты — нет порогов и логики оповещений.
- Пользователи/авторизация — нет механизмов.
- История показаний — показания из API не сохраняются.

### **4. Проблемы монолитного решения**

- Компания позиционирует себя как разработчик системы для регулирования отопления в доме, но самой системы регулирования в продукте - нет, только мониторинг текущих значений. Скорее всего компания выдает себя не за того кем является на самом деле.
- Необходимо реализовать функционал авторизации/аутентификации
- Планируется добавление видеонаблюдения - для него необходим стримминг, который не реализовать через REST API
- Необходимо реализовывать разную логику управления для разных групп параметров, если для условных ворот/света необходима передача команды от пользователя на исполнительный механизм, то для регулировки температуры/влажности - необходима логика учитывающая скорость изменения целевого значения параметра от заданных значений на регулятор. Разная логика требует различных ресурсов, что лучше реализовывать в разных сервисах.
- При различных нагрузках на "видео/тепло/ворота" в монолите масштабировать придется приложение целиком. При этом ресурсозатратное "видео" будет конкурировать с малозатратными "воротами" заа ресурсы.

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql

Для проверки можно использовать Postman коллекцию smarthome-api.postman_collection.json и вызвать:

- Create Sensor
- Get All Sensors

Должно при каждом вызове отображаться разное значение температуры

Ревьюер будет проверять точно так же.
